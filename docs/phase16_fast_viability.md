# 第十六阶段：不改变第一段控制决策的终端可恢复性计算优化

第十五阶段的\`two_stage_viability\`在两个已知及两个曾作历史分析的弱制动种子上都实现严格终点完成，但每周期额外调用最多3次**完整两阶段规划器**；在GitHub Runner上平均88–162ms，不能保证100ms控制周期内实时执行。此阶段重点是**加速，保持候选动作、运动学和严格安全筛选完全不变**，不再挑选更好看的训练种子。

## 等价的两个提前退出

原候选评估顺序：基础全量\`two_stage_bodyframe\`先筛掉所有违规轨迹→按原加权成本取最好的K=3个第一段动作→给每个动作复制指令延迟队列、假设持续0.60秒→从未来状态运行完整严格两阶段搜索→选择原成本最低且**至少有1条严格安全续接**的第一段。

优化版\`two_stage_viability_fast\`仍然执行相同基础全量硬筛选，新的变化仅限：
1. 对每个假设未来状态调用\`exists_strict_continuation\`而不是返回完整\`choose_two_stage\`结果。仍逐次检查原完整顺序：已不可撤销的控制延迟前缀、第一段0.4秒、第二段1.0秒、完整物理制动、停车后6秒。找到第**一条严格可行序列**即可返回True，无需枚举其余序列、计算代价和构造排名。
2. K=3候选已按原成本排序，找到第**一个**可行续接后即可结束探测。旧方法还会探测剩下所有候选，但不能改变前面已经选出的最佳第一段动作。
3. 如果新的探测证明所有K个候选在假设未来状态不可行，和旧版本一样**退回原严格可行基础动作**并记录\`lookahead_no_viable_shortlist=1\`，不会主动接受任何被原硬约束过滤的动作。
4. 如需改变选择，依然调用原\`choose_two_stage(forced_first=...)\`构造被选择命令的完整两阶段轨迹、代价和物理制动/停后占据后备，不放宽任何安全余量。
5. 诊断中的\`lookahead_child_feasible_count=1\`在fast版本表示**找到至少1组证据**，不再代表未来可行组合的精确数量；增加\`lookahead_child_count_is_witness\`标记。其它\`lookahead_probed\`等计数只统计真正执行的探测，故新旧计数不要求相等，**控制指令与物理轨迹要求逐帧完全相等**。

保持后轴偏置0.55m(未经实车标定)、二维合成CV运动目标理想真值、阿克曼自行车模型、道路矩形与目标圆检查、完整制动/延迟/停后占据，严格\`pose_gate\`和35秒截止。绝不把函数名称中的viability当成形式化递归安全保证。

## 对照与统计

- 基础和旧完整前瞻保留；本阶段主要对比完整前瞻\`two_stage_viability\`和加速版本\`two_stage_viability_fast\`。
- 已知双目标弱制动种子0、1；之前做过参数敏感性的种子10、11；以及本阶段未参与设计的种子50、51在\`crossing/narrow/two_targets\`与\`nominal/fast_targets\`组合下的12个独立环境。**不拿老种子当全新留出集**。
- 对所有回合保存完整逐帧轨迹；\`python -m lidar_sim.equivalence_audit\`要求每一控制周期\`time,x,y,yaw,speed,steer,command_speed,command_steer,applied_speed,applied_steer,body_center_x,body_center_y,pose_gate_met\`逐字段浮点容差1e-8且总帧数一致，否则CI失败并提供第一处差异。
- 实际CPU耗时来自同类型GitHub Runner，但并不计入100ms物理周期。即使平均用时<100ms，仍要测单次p95/p99、最坏值以及Jetson端上真实性能，才能说可能满足实时性。
- 逐场景分别报告成功/碰撞/超时/路界出界、耗时和规划时间，并保留所有原始CSV。
