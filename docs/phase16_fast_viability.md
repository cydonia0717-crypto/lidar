# 第十六阶段：保持严格轨迹可行性与动作选择不变的计算优化

## 实际任务

第十五阶段\`two_stage_viability\`在小规模实验中改善了双目标弱制动下的停车侵入问题，但GitHub Runner每周期平均规划耗时约88–162ms，仿真控制周期只有100ms。**原阶段仿真并未将计算时间反馈到控制延迟，所以此前结果属于离线算法效果，不能视为实时10Hz性能。**

第一轮技术目标：不调整候选速度/转向集合、0.6s前瞻、前三名排序、各项硬安全约束或cost权重，也不削减后备制动尾迹和静止6秒检查；仅减少计算**不影响决策的冗余**。

新增\`two_stage_viability_fast\`，与原\`two_stage_viability\`作为独立mode保留，做严格配对：

1. 原\`choose_two_stage\`未来候选检查会遍历全部第一段、第二段动作，计算所有完整可行序列和加权评分；但父级只需知道“下一次重规划是否存在至少一组严格可行序列”。新增\`has_strict_two_stage_successor\`，按照**完全相同顺序和阈值**检查已提交0.25s控制前缀、0.40s第一段、1.00s第二段、真实减速刹停尾迹和刹停后6s目标占据，只要找到第一组完整可行序列便立即返回True；完全无解返回False。其结果应严格等价于原完整规划的\`feasible_count>0\`，但不求无关的成本/排序和其余可行组合数。
2. 基础搜索产生的第一段动作仍按原cost和速度/转角次级键排序，且只取原可行的前\`K=3\`个。按原顺序依次用复制的命令延迟队列推进0.60秒、执行严格碰撞检查与上述存在性检查。如果第一个满足未来可行性，即可立即结束：原实现虽然记录后续候选的可行数量，但总选择规则仍为“原cost最低且下一时刻可行的第一段”。因此其它更靠后的候选不可能改变选择。
3. 其它逻辑完全保留：原搜索已无解时不解除fallback；前三名都无解则选择原严格可行基础动作；如果前瞻改变动作，仍调用原完整两阶段算法对选中的第一段重建并完整验证其最佳第二段/刹车/停后占据后执行。不接受原本不满足硬条件的动作。
4. \`lookahead_probed\`与\`lookahead_viable\`在快速mode中仅统计**实际探测**候选，而不统计未探测的候选；\`lookahead_child_feasible_count\`在快模式是存在标志1，**不是**下一状态可行序列的完整数量。新\`lookahead_existential_fast\`和\`lookahead_early_exit_after_viable\`明示日志口径区别，不得用这些计数跨模式直接推断候选安全比例。

## 严格核验要求

- 单元测试对多个\`seed\`、位置/航向/速度、已有延迟命令队列比较旧完整两阶段\`feasible_count>0\`与存在性判定是否逐点一致；
- 同一状态下验证旧前瞻与快速模式返回**完全相同的第一段命令、完整物理验证轨迹、代价、原可行候选数及fallback**；
- 固定两个已知种子短回合逐帧对照真实施加命令、车辆状态；
- CI完整闭环配对回放双目标弱制动seed0/1、此前见过的seed10/11，以及新增crossing/narrow seed50/51，严格使用统一0.55m物理车身偏置、实际后轴车辆模型、相同目标运动真值及\`pose_gate\`，截止35s。完整输出成功/碰撞/超时/越界与单回合时延，保留所有CSV。
- CI运行时测得的\`compute_ms\`受机器负载影响。重点比较同一回合的动作序列等价、绝对及配对相对耗时；如果快模式仍无法在100ms内完成，继续定位瓶颈。**即使平均<100ms，也不代表p95/p99与Jetson部署合格，更没有把真实规划CPU消耗接入控制延迟。**

## 方法限制

二维合成理想CV目标，目标几何为保守包围圆、离散0.05s硬检查及固定直道路；原后轴偏置0.55m仍是工程假设；没有三维雷达点云、误检漏检、目标跟踪、连续安全或递归可行性证明。这个阶段**仅是原有限深度启发式的等价实现加速**，不是提出新安全理论。


## 逐帧决策等价与控制周期计算时间审计

在完整评估回合保存\`planning_compute_ms\`逐周期测量值，并运行\`python -m lidar_sim.phase16_equivalence_audit\`，从所有\`all_traces/*.csv\`配对对比原\`two_stage_viability\`与新\`two_stage_viability_fast\`。一旦任何时间、位置、姿态、速度、真实施加或下发命令、fallback不同，审计将失败，而非仅检查最终成功率相同。

汇总每一回合的平均、最近秩p95/p99、最大规划耗时，以及100ms时间预算超期的周期数量与比例。这里测的是共享GitHub Runner上的实际Python执行时间；**仿真的真实控制时间仍固定0.1秒，并不自动延后指令**。本阶段目标是减少计算量，并提供部署瓶颈量化证据，不能仅凭平均耗时低于100ms就宣称Jetson 10Hz实时性达标。
