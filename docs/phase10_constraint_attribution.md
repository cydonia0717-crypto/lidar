# 第十阶段：两阶段规划死锁的分阶段拒绝归因

## 为什么先做诊断、暂不更换规划器

[第九阶段实际试验](https://github.com/cydonia0717-crypto/lidar/actions/runs/39213684804)已经明确：双目标nominal/seed0在20–30秒，平均每个控制周期仅有**5组严格可行两阶段序列**，可行的非零首段目标速度占比为**0%**，小车每次都发送目标速度0，实际前进0m。它没有触发紧急制动，因为已有的停车类动作满足该模型的有限时域检查。

**这不是单纯的成本排序问题**。在现有有限搜索集合与安全约束下，没有可参与评分的前进序列。第九阶段额外奖励首段进度反而使留出集碰撞增加，故本阶段不继续增大“前进奖励”或放松安全限制，而是定位候选究竟在哪个阶段被排除。

## 新增分阶段日志

只对原\`two_stage\`增加诊断，使用与实际碰撞筛选**完全一致**的道路宽度、车辆包围圆、动态CV目标位置、预测附加距离和离散采样时刻。每个控制周期记录：

- \`reject_prefix_{road,obstacle}\`：已发出指令形成的延迟前缀越界或相撞；
- \`reject_first_{road,obstacle}\`：第一段目标速度/转角执行0.4秒被拒绝（以“第一段候选”为计数单位）；
- \`reject_second_{road,obstacle}\`：某组第二段动作执行1.0秒被拒绝（以“两阶段组合”为计数单位）；
- \`reject_brake_{road,obstacle}\`：两阶段动作执行后，物理制动尾迹不满足安全约束；
- \`reject_hold_{road,obstacle}\`：刹停后继续静止6秒，停车位置与动态目标冲突；
- \`feasible_first_actions\`、\`max_feasible_first_speed\`、\`moving_first_action_feasible\`：有多少首段动作至少存在一个严格可行的第二段续接，是否还可以前进；
- 原有\`feasible_count\`和\`rejected_by_backup\`语义不变，\`Plan.rejection_counts\`作为额外解释日志使用，不改变任何原规划评分和所选动作。

**重要：不同阶段的拒绝计数单位不同，不可把它们直接相加当“失败百分比”**。每个候选序列只记录**第一次无法满足的阶段**，不再继续评价后续阶段。发生道路、障碍物同时违规时，以相同离散扫描顺序下的第一处违规归因。

## 复现实验

\`\`\`bash
pip install -e '.[dev]'
pytest -q

python -m lidar_sim.rejection_diagnostics --scenario two_targets \\
 --stress nominal --seed 0 --max-time 30 \\
 --output results/rejection-forensics
\`\`\`

输出\`rejection_windows.json\`和\`rejection_windows.csv\`，按5秒窗口汇总车辆真实x方向进度、控制速度、可行两阶段序列数量、仍有安全前进动作的周期占比，以及每个阶段×冲突类别的拒绝次数。

## 应该怎样解释

- 如果**第一段或第二段道路违规**主导：优先检查保守车辆包围圆、走廊宽度、离散前轮转角采样，以及是否需要精准车辆矩形/扫掠体几何；
- 如果**第一段/第二段目标碰撞**主导：检查目标CV预测和时间对齐的可穿越时间窗口，并优化候选动作组合的时域覆盖；
- 如果**制动尾迹**主导：检查制动能力、前轮转角保持假设、制动阶段动态目标占据和真实控制延迟；
- 如果**停车后停驻占据**主导：检查6秒固定位置预测是否过于保守，是否应通过终端后备可行运动集而非“固定停车位置安全”建模；
- 即使某一阶段拒绝次数最多，也不能忽略不同阶段各自的候选尝试数；需要在独立场景中重复，避免把单种子结果当作普遍结论。

仍然是合成二维理想CV目标、离散保守车辆圆，**不构成真实雷达与实车安全验证**。
