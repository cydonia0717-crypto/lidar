# 第17阶段复核：实测CPU负载波动与固定时延下的非单调闭环失效

## 核心结论（独立于前一轮运行）

相同GitHub代码、几何和理想CV场景，在不同Runner工作流中用**每次实际CPU墙钟耗时**反馈控制，闭环终局并非一定可复现：

- 先前 [Run #39763806338](https://github.com/cydonia0717-crypto/lidar/actions/runs/39763806338)，优化前瞻 `two_targets/weak_brake/seed0` 的 `measured` 模式于 **16.70s碰撞**。
- 最新 [Run #39766856736](https://github.com/cydonia0717-crypto/lidar/actions/runs/39766856736)（[原始Artifact #12421253003](https://github.com/cydonia0717-crypto/lidar/actions/runs/39766856736/artifacts/12421253003)），相同场景/模式的 `measured` **16.70s成功**，仅跳过1个控制时隙。
- 这不矛盾：`measured` 的定义是把**当前Runner本次计算耗时序列**施加给车辆，每次运行输入的时延序列不同。事件时序改变会让闭环动作分叉。不能把一次时延序列下的碰撞误称为该算法的稳定碰撞概率或由代码改动直接引起的回归。

最新第17阶段36回合 `none → measured` 汇总：

| 控制器 | 无反馈成功 | 最新实测反馈成功 | 最新实测反馈碰撞 | 其它未成功结局 |
|---|---:|---:|---:|---|
| 原双阶段 `two_stage_bodyframe` | 3/6 | 5/6 | 0/6 | seed10 超时 |
| 冻结15前瞻 `two_stage_viability_phase15` | 6/6 | 6/6 | 0/6 | 0 |
| 优化16前瞻 `two_stage_viability` | 6/6 | 6/6 | 0/6 | 0 |

最新 `measured` 累计丢失的100ms控制时隙：原两阶段0，第15阶段前瞻349，第16阶段优化前瞻1。这里每个控制器承受的CPU耗时不同，**不能作为公平的算法安全性排序**。

### 本轮确定性固定时延扫描

`two_targets / weak_brake / seed0`、同一物理车身/目标真值、35s截止、100ms控制周期；分别固定每次规划所需的**实际假定耗时**（ms），两个规划器承受相同的计算时长。每次指令仍有额外0.25s的传输/执行延迟。

| 每次计算固定时延 | 原双阶段：结局（终止s） | 优化前瞻：结局（终止s） |
|---:|---|---|
| 0ms | 成功 30.10 | 成功 16.70 |
| 20ms | 成功 18.00 | 成功 16.80 |
| 40ms | 成功 18.80 | **碰撞 18.25** |
| 60ms | 成功 18.50 | **碰撞 18.96** |
| 80ms | **碰撞 16.08** | **碰撞 18.28** |
| 100ms | 成功 18.70 | 成功 19.60 |
| 120ms | **碰撞 16.17** | **碰撞 16.17** |
| 160ms | **碰撞 18.00** | **碰撞 18.00** |

**没有单一单调的安全计算时延阈值。** 对优化前瞻而言，40/60/80ms失败而100ms成功，120/160ms再失败。说明输入控制执行时序对动态目标相遇相位、停止位置和后续可行性存在非连续、非单调的影响；属于**当前离散决策系统和特定目标轨迹的数值观察**，尚不是普遍性质或理论证明。

从原始 `fixed_40ms` 优化前瞻 trace 检查：
- 最终碰撞时刻 **18.25s**，车体静止于约 `(11.811, -0.715)m`，采样净空 `-0.01414m`。
- 约 **9.7s** 首次触发 `unsafe_fallback`；最终十几个决策时隙持续零速、车辆位置不变，净空在17.0～18.2s逐步收缩到接近0，随后发生静止目标侵入型碰撞。
- 这一固定40ms试验**没有跳过100ms时隙**。因此，即使CPU耗时一直小于控制周期，在指令提交端额外加入40ms也足以改变最终动作；仅看 `missed_control_ticks` 会漏掉重要的危险机制。

### 可复现实验设计

原先 `phase17_replay.py` 已经在最新成功的CI中通过：对本次 `measured` seed0 的三个控制器按各自记录的逐决策CPU时延序列重放，逐帧误差均为0。这只证明“**给定完全相同的时延序列，轨迹可以确定性回放**”，不能证明不同Runner的`measured`本身会相同。

后续新增（需以对应新CI为准）：
1. `phase17_fixed_analysis.py` 对同一case下多个模式使用的固定时延网格一致性、执行日志时延、结局反转和末尾静止被侵入进行严格校核，输出 `phase17-fixed-sweep-audit.csv`；
2. `phase17_replay --source-policy fixed_40ms` 针对固定40ms碰撞进行跨Runner确定性轨迹重放，输出 `phase17-fixed40-replay.csv`；
3. 针对非单调变化、CSV有效性及调度一致性增加Pytest回归。

这两套复现方式语义不同：**固定时延**回答“在共同指定的计算预算下会怎样”；**时延序列回放**回答“特定一段已经观测到的CPU抖动是否会独立重现同一物理轨迹”。

### 科学边界

所有结果仍来自二维理想CV真值、有限粒度碰撞检测和100ms仿真周期，不是Jetson Orin NX硬件实时性能或真实场地安全性证据。原有0.25s指令延迟被假设为CPU耗时之外的独立延迟；若实车测量已包含CPU计算，直接相加会重复计时。后续的第17阶段应优先建立同一计算预算下的延迟感知预测及回归，而第18阶段再使用独立种子扩大样本。
