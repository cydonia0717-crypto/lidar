# 第九阶段实际诊断和先导实验：第一段进度奖励反而增加碰撞

数据来源：[GitHub Actions Run 39212979933](https://github.com/cydonia0717-crypto/lidar/actions/runs/39212979933)；**59项单元测试通过**，8次历史种子配对仿真+8次独立留出种子配对仿真完成；历史失败轨迹诊断已运行。所有结果均为合成二维理想CV运动仿真，不是雷达实测和形式化安全证明。

## 1. 实际30秒超时轨迹：推迟第二段不是全部原因

\`two_targets/nominal/seed0/two_stage\`，5秒窗口来自真实物理积分：

| 时间 | 自车x位移m | 第一段速度目标=0比例 | 规划第二段平均目标速度(m/s) | 第一/第二段预测平均进度(m) |
|---|---:|---:|---:|---:|
| 0–5s | 9.474 | 0% | 1.635 | 0.724 / 1.672 |
| 5–10s | 2.777 | 20% | 0.924 | 0.259 / 0.712 |
| 10–15s | 2.506 | 20% | 0.408 | 0.179 / 0.329 |
| 15–20s | 0.029 | 92% | 0.000 | 0.006 / 0.002 |
| 20–25s | 0 | 100% | 0.000 | 0 / 0 |
| 25–30s | 0 | 100% | 0.000 | 0 / 0 |

20秒后第一段和第二段都规划停车，而且日志没有触发\`emergency_brake\`。这**推翻了**“规划器始终承诺第二段前进却不执行，导致30秒超时”的狭义假设。真正待分辨的问题是：

- 当前已经**只剩停车类候选序列能够满足所有约束**，则需改变轨迹几何/搜索范围/安全占据构造；
- 当前仍有严格可行的前进行为，却因当前成本和短期滚动策略不断选停车，则需重新设计代价、长期进度/逃逸可行性。

因此追加日志\`feasible_pairs\`、\`feasible_first_actions\`、\`max_feasible_first_speed\`及\`stopped_choice_with_moving_option\`，并在\`stall_windows.csv\`直接统计“有可行前进首段却选择停”的比例；这些是后续诊断依据，并非自行假设无解。

## 2. 第一段可执行进度奖励：历史与独立场景均无收益

为了测试上述假设，保留原\`two_stage\`并新增\`two_stage_commit\`，只对**严格安全的序列**增加第一段进度奖励项，权重预先指定7.0。未放松任何现有制动/道路/移动目标硬约束。

| 集合与算法 | 成功 | 碰撞 | 超时 |
|---|---:|---:|---:|
| 历史0、1种子，两种压力，原two_stage（4次） | 2 | 0 | 2 |
| 历史0、1种子，两种压力，two_stage_commit（4次） | 1 | 1 | 2 |
| 留出10、11种子，两种压力，原two_stage（4次） | 0 | 1 | 3 |
| 留出10、11种子，两种压力，two_stage_commit（4次） | 0 | 2 | 2 |

具体负面样本：
- \`nominal/seed1\`：原本14.0秒成功，新版16.9秒碰撞；
- \`nominal/seed10\`：原本30秒超时，新版18.7秒碰撞；
- \`weak_brake/seed10\`：原本30秒超时，新版16.2秒碰撞；
- \`weak_brake/seed11\`：原本16.6秒碰撞，新版30秒超时。

这不是更好的通行决策；“少超时”有时仅仅是提前撞上障碍物。**明确不建议把\`two_stage_commit\`合并到正式安全算法**。作为能复核的失败消融保留。

## 3. 下一步：停止堆叠奖励权重

优先用新日志区分候选严格无解与安全前进动作被成本忽视这两种机制。之后如有必要再检查：

1. 车辆沿单向x道路目标达到判定是否误把侧向/绕行活动当停滞；
2. 目标未来长时间停后6秒占据是否对静止目标/骑行者过于保守；
3. 单一保守包围圆是否使本来物理可绕行的道路被判狭窄；
4. 仅5组前轮角度和5组速度使连续动作空间出现采样空洞；
5. 只执行first而反复改变first造成非递归可行、动作来回震荡。

如果日志显示严格安全前进候选**根本不存在**，调进度偏好也无法创造动作；应优先改善轨迹候选表示、道路和车体几何模型及有限时域安全定义，再重新设计独立的实验。
